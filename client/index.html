🔑 Strict Pass-by-Value in One Sentence (JLS §8.4.1)

Java ALWAYS passes by value. Passing an object copies the 4-byte debit card address chip (e.g. 0x4A2F), NEVER the physical central bank vault! Reassigning the card inside a method only buys a card for the helper method; caller variables remain untouched.

🏛️ TIER 1: OFFICIAL SPECIFICATIONS (JVMS & JLS)

1. JLS §4.12.1 (Variables of Primitive Type): A primitive variable always holds a raw value of that exact primitive type directly in its memory slot, never a reference or pointer. For int, this is a 32-bit signed two's-complement integer.

2. JLS §4.12.2 (Variables of Reference Type): A reference variable always holds either null or a reference to an object. It never holds the object itself!

3. JLS §4.12.3 (Kinds of Variables): Local variables (declared in methods) are stored in the JVM Stack Frame. Instance variables (fields declared in classes) reside inside the object on the Heap.

4. JVMS §2.6.1 (Local Variable Array): A method's local variables reside in its private stack frame. Controlled by the CPU RSP hardware register with zero GC overhead.

5. JVMS §2.5.3 (Heap Storage Pool): All object instances and arrays are allocated on the shared heap, managed by automatic Garbage Collection.

6. JLS §8.4.1 (Formal Parameters - Pass-By-Value): Java is strictly Pass-by-Value without exception. An argument's value is evaluated and copied into the parameter slot. For primitives, raw bits are copied; for objects, the 32-bit memory address is copied.

7. HotSpot 64-bit Object Header: 8-byte Mark Word (HashCode, GC Age, Locks) + 4-byte Compressed Klass Word (pointing to Metaspace) + fields + 8-byte boundary alignment padding.

🌐 TIER 2: INDUSTRY & INTERNET ANALYSIS

Common Internet Misconception: "All primitives go to the Stack; all objects go to the Heap."

The Correction (Cay Horstmann - Core Java & Project Valhalla): Declaration context, not data type, determines physical storage location! A local primitive (int deposit = 500) lives in the stack frame. But an instance primitive field (class BankAccount { int balance = 1000; }) lives physically on the Heap inside the BankAccount object's instance payload at byte offset 12!

MIT 6.005 / 6.102 (Software Construction by Rob Miller): Snapshot diagrams model variables as named slots on the stack pointing via arrows (addresses) to mutable object bubbles on the heap. Multiple slots pointing to the same bubble is Aliasing.

Joshua Bloch (Effective Java Item 50): Defend against accidental aliasing through immutable structures or defensive copies.

JIT Escape Analysis & Scalar Replacement: If an object does not escape a method, the HotSpot C2 JIT compiler eliminates heap allocation and places primitive fields directly in CPU registers or stack slots.

🧠 TIER 3: 20+ YR MASTER TEACHER SYNTHESIS

The 3 JVM Worlds of Java: In BankAccount account = new BankAccount("Alice", 1000);:

  • BankAccount (Capital 'B'): Metaspace Class Blueprint (JVMS §2.5.4). Factory schematics, bytecode methods (deposit(), withdraw()) in native RAM. You cannot swipe a blueprint at an ATM!
  • account (Lowercase 'a'): Stack Debit Card (JVMS §2.6.1). 4-byte address slot holding 0x4A2F. Cleared in 0.001ms when method returns.
  • new BankAccount("Alice", 1000): Living Central Bank Vault on Heap (JVMS §2.5.3). 16-byte memory block (8B Mark Word + 4B Klass Word + 4B balance field).

The Definitive Truth on Variables: main's local variable int deposit = 500 on the Stack is 100% physically isolated from the BankAccount object's field int balance = 1000 on the Heap. Calling processTransaction(account, deposit) passes copies of the debit card handle and deposit number. Modifying the local parameter never touches caller variables.
